Observation: this was discovered while updating the Dockerfile COPY list for the app.py decomposition (DECISION-20260928-165752-577104). The Dockerfile copies only named root modules (app.py, db.py, stt_worker.py, reconciler.py, and now settings.py, routes/, services/). It has never copied export.py. The start_export handler (POST /v1/sessions/{session_id}/export/{fmt}, now in routes/sessions.py) imports export_pdf/export_video lazily inside its background task. In the container that import raises ModuleNotFoundError, which the task's except block catches: the endpoint still returns {status: started}, and the status endpoint later reports status=error with a 'No module named export' message. The feature therefore fails silently in containerised deployments and works only when run from a source checkout. This predates the refactor, and the refactor deliberately left it unfixed to preserve behaviour. A likely fix is adding export.py to the Dockerfile COPY line; export.py may also need runtime dependencies such as headless-browser or ffmpeg tooling that the slim image lacks, so this should be verified with a container build and an export smoke test.
